# Employee Management System (FastAPI)

A simple REST API for managing employee records, built with **FastAPI**, **SQLAlchemy**, and **SQLite**, with **JWT-based authentication** protecting the employee-listing route.

## Features

- Full CRUD for employee records (create, read, update, delete)
- SQLite database via SQLAlchemy ORM
- Login endpoint that issues a signed JWT (30-minute expiry)
- A protected route that requires a valid token to access

## Tech Stack

- [FastAPI](https://fastapi.tiangolo.com/) — web framework
- [SQLAlchemy](https://www.sqlalchemy.org/) — ORM
- [SQLite](https://www.sqlite.org/) — database
- [python-jose](https://github.com/mpdavis/python-jose) — JWT encoding/decoding
- [Uvicorn](https://www.uvicorn.org/) — ASGI server

## Setup

**1. Clone or download the project, then create a virtual environment (recommended):**
```bash
python -m venv venv
source venv/bin/activate      # Windows: venv\Scripts\activate
```

**2. Install dependencies:**
```bash
pip install fastapi uvicorn sqlalchemy python-jose
```

**3. Run the server:**
```bash
uvicorn main:app --reload
```

The API will be available at `http://127.0.0.1:8000`.
Interactive docs (Swagger UI) are auto-generated at `http://127.0.0.1:8000/docs`.

> The SQLite database file (`emp_data.db`) is created automatically on first run, along with the `employee` table.

## API Endpoints

| Method | Endpoint              | Auth required | Description                          |
|--------|------------------------|:--------------:|----------------------------------------|
| POST   | `/create_emp`          | No             | Create a new employee                  |
| GET    | `/emp_data/{emp_id}`   | No             | Get one employee by ID                 |
| PUT    | `/update_emp/{emp_id}` | No             | Update an employee's name/password     |
| DELETE | `/delete_emp/{emp_id}` | No             | Delete an employee                     |
| POST   | `/login/{emp_id}`      | No             | Log in, returns a JWT access token     |
| GET    | `/emp_data`             | **Yes**        | List all employees (requires token)    |

### Request parameters

All input fields (`name`, `password`, etc.) are sent as **query parameters**, not a JSON body — for example:

```
POST /create_emp?name=Vaidik&password=1234
```

### Example: Create an employee
```bash
curl -X POST "http://127.0.0.1:8000/create_emp?name=Vaidik&password=1234"
```

### Example: Log in
```bash
curl -X POST "http://127.0.0.1:8000/login/1?name=Vaidik&password=1234"
```
Returns a JWT access token (a plain string).

### Example: Access the protected route
```bash
curl -H "token: <your_jwt_token>" "http://127.0.0.1:8000/emp_data"
```

## Authentication Flow

1. Create an employee via `POST /create_emp`.
2. Log in via `POST /login/{emp_id}` with that employee's `name` and `password`.
3. On success, a signed JWT is returned (valid for 30 minutes).
4. Send that token in the `token` header on requests to `GET /emp_data`.
5. Invalid, missing, or expired tokens return `401 Unauthorized`.

## Known Limitations

This project is built for learning purposes. A few things to be aware of before using it beyond that:

- **Passwords are stored in plain text.** In a real application, passwords should be hashed (e.g. with `passlib`/`bcrypt`) before storing, and verified by comparing hashes — never raw strings.
- **Inputs are query parameters, not a JSON body.** A production-style API would typically accept a Pydantic model in the request body instead (e.g. `{"name": ..., "password": ...}`).
- **The secret key is hardcoded.** `SECERT_KEY` should come from an environment variable in any real deployment, not be committed in source code.
- **`/login/{emp_id}` requires knowing your own database ID upfront**, which isn't typical — most login flows look up the user by name/email alone.
