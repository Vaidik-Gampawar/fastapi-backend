# 8. Response Models + Data Validation + Hide Sensitive Data

## What this code does
Introduces `response_model` — a way to control exactly what data goes **out** to the client, separate from what your function internally works with.

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class User(BaseModel):
    name: str
    age: int
    password: str

class UserResponse(BaseModel):
    name: str
    age: int

@app.get("/user", response_model=UserResponse)
def get_user():
    return {
        "name": "vaidik",
        "age": 21,
        "password": "abc"
    }
```

## Key concepts

**1. Two models, two purposes**
- `User` → represents the **full** data (including sensitive fields like `password`)
- `UserResponse` → represents what's **safe to send back** to the client (no `password`)

This is a common real-world pattern: your internal/full data shape is rarely identical to what you expose over the API.

**2. `response_model=UserResponse`**
```python
@app.get("/user", response_model=UserResponse)
```
This tells FastAPI: "no matter what my function returns, filter and validate it against `UserResponse` before sending it out."

**3. What actually happens here**
The function returns a dict with **three** keys (`name`, `age`, `password`), but the response the client receives only has **two** (`name`, `age`). FastAPI:
1. Takes the returned data
2. Matches it against `UserResponse`'s fields
3. **Strips out any field not in `UserResponse`** (here, `password`)
4. Sends only the filtered, validated result

So even though the function is sloppy and returns the password, it **never actually leaves the server**. This is a real security feature, not just a formatting one.

**4. Why this matters (security angle)**
It's very easy to accidentally leak sensitive data — passwords, internal flags, database IDs, etc. — by just returning your internal object as-is. `response_model` acts as a **safety filter** at the API boundary, so even a mistake in your function body won't expose stuff you didn't mean to.

**5. Bonus: it also documents your API**
Because `response_model` is a Pydantic model, it also shows up in the auto-generated `/docs` — anyone looking at your API's documentation sees exactly what shape the response will be, without needing to read your function's code.

## Quick recap
- `response_model=SomeModel` filters and validates outgoing data, independent of what the function returns internally
- Fields not present in the response model are automatically stripped from the response
- Great pattern: one model for full/internal data, another (leaner) model for what's actually sent to clients
- Also improves `/docs` — the response shape is documented automatically
