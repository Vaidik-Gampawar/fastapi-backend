# 13. SQLite Database Integration + Setup + SQLAlchemy

## What this code does
Moves away from the in-memory list (lectures 6–7) to an actual **persistent database** — using Python's built-in `sqlite3` module to create a real `todos` table.

```python
import sqlite3
from fastapi import FastAPI

app = FastAPI()

conn = sqlite3.connect("test.db", check_same_thread=False)

cursor = conn.cursor()

cursor.execute("""
CREATE TABLE IF NOT EXISTS todos (
    id INTEGER PRIMARY KEY,
    title TEXT,
    completed TEXT
)
""")

conn.commit()

@app.get("/")
def home():
    return {"message": "SQLite3 Connected"}
```

> **Note:** the lecture title mentions SQLAlchemy, but this specific file only uses the raw built-in `sqlite3` module — no SQLAlchemy code here yet. These notes cover what's actually in the file; SQLAlchemy (a more powerful ORM layer) is likely the *next* step in this lecture series.

## Key concepts

**1. Why move off the in-memory list**
Back in lecture 6, `todos = []` reset every time the server restarted. `sqlite3` gives you a **real file-based database** (`test.db`) — data survives restarts, and you get proper querying instead of manually looping through a Python list.

**2. `sqlite3.connect("test.db", check_same_thread=False)`**
- `sqlite3.connect("test.db")` → opens (or creates, if it doesn't exist) a database file named `test.db` in your project folder
- `check_same_thread=False` → SQLite normally restricts a connection to the thread that created it. FastAPI can handle requests across multiple threads, so this flag relaxes that restriction so the same connection can be reused safely across requests. (Note: for a real production app, using a single global connection like this isn't ideal — connection pooling or per-request connections are safer, which is likely why the lecture is heading toward SQLAlchemy next.)

**3. `cursor = conn.cursor()`**
A **cursor** is your tool for actually executing SQL commands and fetching results through the connection. Think of `conn` as "the open database file" and `cursor` as "the thing that lets you run SQL on it."

**4. Creating the table**
```sql
CREATE TABLE IF NOT EXISTS todos (
    id INTEGER PRIMARY KEY,
    title TEXT,
    completed TEXT
)
```
- `CREATE TABLE IF NOT EXISTS` → only creates the table if it doesn't already exist, so re-running this code on server restart won't error out or wipe existing data
- `id INTEGER PRIMARY KEY` → a unique identifier for each row, and SQLite will auto-increment it if not provided
- `title TEXT` → the todo's text
- `completed TEXT` → stores completion status *(worth noting: this is `TEXT`, not a boolean/integer — SQLite doesn't have a true boolean type, so this is commonly stored as `"true"/"false"` text or `0/1` integers depending on convention)*

**5. `conn.commit()`**
SQL changes (like creating a table, or later, inserting/updating data) aren't permanently saved until you `commit()`. This writes the change to the actual database file.

**6. Where this code runs**
This whole setup block — connect, create cursor, create table, commit — runs at **import time**, i.e. once when the FastAPI app starts up, not inside any route. That's appropriate for one-time setup like "make sure the table exists," as opposed to per-request logic.

## What's likely coming next
Given the lecture title references SQLAlchemy, the natural next steps from here are probably:
- Writing actual `INSERT`, `SELECT`, `UPDATE`, `DELETE` SQL inside your routes (raw SQL version)
- Then likely refactoring to **SQLAlchemy**, an ORM that lets you work with Python classes/objects instead of writing raw SQL strings — while also handling connections more safely per-request

## Quick recap
- `sqlite3.connect("file.db")` → opens/creates a SQLite database file
- `check_same_thread=False` → needed to safely reuse one connection across FastAPI's multiple request threads
- `cursor.execute(sql)` → runs a SQL command
- `CREATE TABLE IF NOT EXISTS` → safe to re-run without wiping existing data
- `conn.commit()` → actually saves changes to the database file
- This setup code runs once at startup, not per-request
