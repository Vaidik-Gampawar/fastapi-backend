# 15. CREATE Operation with Database

## What this code does
Adds the first real database operation on top of lecture 14's setup: **actually inserting a new row** into the `todos` table using SQLAlchemy.

```python
@app.post("/todos")
def create_todo(title: str, db: Session = Depends(get_db)):
    todo = Todo(title=title, completed="False")
    db.add(todo)
    db.commit()
    db.refresh(todo)

    return {
        "message": "Todo Created",
        "data": todo
    }
```
*(the setup above this — engine, session, `Todo` model, `get_db()` — is identical to lecture 14)*

## Key concepts

**1. `title: str` here is a query parameter — worth noticing**
```python
def create_todo(title: str, db: Session = Depends(get_db)):
```
Recall the rule from lecture 7: a plain type (`str`) that isn't in the path and isn't a Pydantic model → **query parameter**. So this endpoint is called like:
```
POST /todos?title=Buy%20groceries
```
This works, but it's a step back from lecture 4/6's approach of using a `Todo(BaseModel)` for the request body. For a real project you'd likely want a Pydantic schema here instead (e.g. `todo: TodoCreate` in the body) — this version is probably kept simple on purpose since the focus of this lecture is the *database* operation, not request design.

**2. Creating a model instance — `Todo(title=title, completed="False")`**
```python
todo = Todo(title=title, completed="False")
```
This creates an **in-memory Python object** representing a row — but nothing has touched the database yet at this point. `Todo` here is the SQLAlchemy model class from lecture 14, being instantiated like a normal Python class.

**3. `db.add(todo)`**
Stages the new object to be inserted — tells the session "this object should become a new row," but still doesn't write to the database yet. Think of it as "preparing" the change.

**4. `db.commit()`**
This is the step that **actually executes the SQL `INSERT`** and saves it permanently to the database file — same role as `conn.commit()` in the raw `sqlite3` version (lecture 13), just through the ORM session now.

**5. `db.refresh(todo)`**
After committing, the `todo` Python object doesn't automatically know about database-generated values — most importantly, the auto-generated `id`. `db.refresh(todo)` re-fetches the row from the database and updates the `todo` object in place, so `todo.id` is now populated correctly.

**6. The full lifecycle, in order**
```
1. Todo(...)     → build the object in memory
2. db.add(...)   → stage it for insertion
3. db.commit()   → write it to the database
4. db.refresh(...) → sync the object with what the DB actually stored (e.g. get the new id)
```
This four-step pattern (`create → add → commit → refresh`) is the standard SQLAlchemy flow for creating a new row, and you'll see it repeated for most "create" operations.

**7. Returning a SQLAlchemy object directly**
```python
return {"message": "Todo Created", "data": todo}
```
FastAPI is smart enough to serialize a SQLAlchemy model object into JSON automatically for the response — even though `todo` isn't a plain dict or Pydantic model. (Later lectures may formalize this with a `response_model`, similar to lecture 8, for more control over exactly which fields get returned.)

## Quick recap
- `ModelClass(field=value, ...)` → builds an in-memory row object, not yet saved
- `db.add(obj)` → stages it for insertion
- `db.commit()` → actually writes the change to the database
- `db.refresh(obj)` → updates your Python object with database-generated values (like auto-incremented `id`)
- This create → add → commit → refresh sequence is the standard pattern for inserting data with SQLAlchemy
