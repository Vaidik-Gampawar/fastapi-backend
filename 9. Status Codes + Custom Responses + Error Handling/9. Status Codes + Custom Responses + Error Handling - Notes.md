# 9. Status Codes + Custom Responses + Error Handling

## What this code does
Introduces **proper HTTP status codes** — both setting a custom success code and raising real error codes, instead of returning `{"error": "..."}` with a default `200 OK` (the gap flagged back in lecture 6).

```python
from fastapi import FastAPI, status, HTTPException
from pydantic import BaseModel

app = FastAPI()

@app.post("/create_user", status_code=status.HTTP_201_CREATED)
def create_user():
    return {"message": "User Created"}

@app.get("/users")
def get_users():
    return {
        "status": "Success",
        "message": "User Fetched",
        "data": {"name": "vaidik", "age": 21}
    }

@app.get("/users/{user_id}")
def get_user(user_id: int):
    if user_id != 1:
        raise HTTPException(status_code=404, detail="User not found")
    return {
        "message": "User Found",
        "data": {"name": "vaidik", "age": 21}
    }
```

## Key concepts

**1. Why status codes matter**
HTTP status codes tell the client *what kind* of thing happened, without them having to parse your response body:
- `2xx` → success
- `4xx` → client made a mistake (bad input, not found, unauthorized, etc.)
- `5xx` → server made a mistake

By default, FastAPI returns `200 OK` for every successful response — even for a `POST` that creates something, where `201 Created` is more accurate.

**2. Setting a custom success status — `status_code=`**
```python
@app.post("/create_user", status_code=status.HTTP_201_CREATED)
```
This overrides the default `200` and tells FastAPI to return `201 Created` instead — the correct convention for "a new resource was successfully created."

**3. The `status` module**
```python
from fastapi import status
```
Instead of hardcoding magic numbers like `201`, FastAPI gives you readable constants: `status.HTTP_201_CREATED`, `status.HTTP_404_NOT_FOUND`, `status.HTTP_400_BAD_REQUEST`, etc. Same effect, but much more readable and less error-prone than remembering raw numbers.

**4. Raising real errors — `HTTPException`**
```python
if user_id != 1:
    raise HTTPException(status_code=404, detail="User not found")
```
This is the fix for the pattern in lecture 6! Instead of returning `{"error": "..."}"` with a sneaky `200 OK`, `raise HTTPException(...)`:
- Immediately stops the function
- Sends back the specified status code (here, `404`)
- Sends back a JSON body: `{"detail": "User not found"}`

This is the **correct, idiomatic FastAPI way** to signal errors — the client (and tools like `/docs`) can now tell instantly that something went wrong, just from the status code.

**5. `raise` vs `return`**
Note the difference: normal responses use `return`, but errors use `raise HTTPException(...)`. Raising immediately halts execution — no risk of accidentally continuing and returning a "success" body after an error condition.

## Quick recap
- `status_code=` on a route decorator → sets the HTTP status for a successful response (e.g. `201` for creation)
- `from fastapi import status` → gives readable constants instead of raw numbers
- `raise HTTPException(status_code=..., detail=...)` → the correct way to return errors, with the right status code and message
- This directly fixes the earlier Todo app pattern (lecture 6) that returned errors with a misleading `200 OK`
