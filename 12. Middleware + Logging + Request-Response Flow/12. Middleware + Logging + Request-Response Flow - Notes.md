# 12. Middleware Explained + Logging + Request/Response Flow

## What this code does
Introduces **middleware** — code that runs on **every single request**, before and after your actual route logic — using it here to log how long each request takes.

```python
from fastapi import FastAPI, Request
import time

app = FastAPI()

@app.middleware("http")
async def log_middleware(request: Request, call_next):
    start_time = time.time()

    response = await call_next(request)

    complete_time = time.time() - start_time

    print(f"Path: {request.url.path} | Time: {complete_time}")

    return response
```

## Key concepts

**1. What middleware is**
Middleware sits **between** the incoming request and your route function — it wraps around *every* request/response, no matter which route is hit. Think of it as a layer the request has to pass through on the way in, and the response passes through on the way out.

**2. The simple version (commented out) shows the shape**
```python
@app.middleware("http")
async def my_middleware(request: Request, call_next):
    print("Request Sent")
    response = await call_next(request)
    print("Response Sent")
    return response
```
This is the bare skeleton, and it reveals the key structure: anything **before** `call_next(request)` runs *before* your route executes; anything **after** runs *after* your route has already produced a response.

**3. `@app.middleware("http")`**
This decorator registers the function as middleware for all HTTP requests. Unlike `Depends()` (lecture 11), which you attach to specific routes, middleware applies **globally** — you don't add it per-route, it just runs for everything automatically.

**4. `call_next(request)` — the crucial piece**
```python
response = await call_next(request)
```
This is what actually **passes control to the next step** — either another middleware, or (eventually) the matching route function. Without calling this, the request would never reach your route at all. It's `await`ed because it's asynchronous.

**5. The logging example, step by step**
```python
start_time = time.time()          # 1. Record time before route runs
response = await call_next(request)  # 2. Let the route actually execute
complete_time = time.time() - start_time  # 3. Measure how long it took
print(f"Path: {request.url.path} | Time: {complete_time}")  # 4. Log it
return response                   # 5. Send the response back to the client
```
This pattern — timing, logging, then returning the response — is extremely common in real APIs for performance monitoring and debugging.

**6. `request.url.path`**
The `Request` object gives you access to details about the incoming request. `request.url.path` specifically gives you just the path (e.g. `/users/5`) without the full URL, host, or query string — handy for clean logs.

**7. Why `async def` and `await`**
Middleware functions must be `async` because `call_next` is asynchronous — it needs to `await` the rest of the request-handling pipeline (route function, any other middleware) to actually finish before it can return a response.

## Common real-world uses of middleware
- Logging requests/response times (this example)
- Authentication checks (as an alternative to per-route `Depends()`)
- Adding custom headers to every response (e.g. CORS headers)
- Catching and formatting errors globally
- Rate limiting

## Quick recap
- `@app.middleware("http")` → registers a function that runs for **every** request, globally
- Code before `call_next(request)` → runs before the route
- `call_next(request)` → passes the request forward to the actual route (must be `await`ed)
- Code after `call_next(request)` → runs after the route has responded, before the client receives it
- Must return the `response` at the end, or the client gets nothing back
