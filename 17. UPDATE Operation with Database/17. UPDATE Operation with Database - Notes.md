# 17. UPDATE Operation with Database

## What this code does
Adds the "U" of CRUD — updating an existing row in the database, building on the same `Todo`/`get_db()` setup from lectures 14–16.

```python
@app.put("/todos/{todo_id}")
def update_todo(todo_id: int, title: str, completed: str, db: Session = Depends(get_db)):
    todo = db.query(Todo).filter(Todo.id == todo_id).first()

    if not todo:
        raise HTTPException(status_code=404, detail="Todo Not Found")

    todo.title = title
    todo.completed = completed
    db.commit()
    db.refresh(todo)

    return {
        "message": "Todo Updated",
        "data": todo
    }
```

## Key concepts

**1. Step 1 — find the row first**
```python
todo = db.query(Todo).filter(Todo.id == todo_id).first()
```
Same lookup pattern as lecture 16's `GET /todos/{todo_id}`. You can't update something without first fetching the actual database object to work with — this `todo` is a "live" SQLAlchemy object tied to the session, not just a plain dict.

**2. The same "not found" guard, reused**
```python
if not todo:
    raise HTTPException(status_code=404, detail="Todo Not Found")
```
Identical pattern to the read route — worth noticing how consistent this check looks across create/read/update/delete now that you're using `HTTPException` properly (lecture 9) instead of the old silent-`200` errors.

**3. Step 2 — mutate the object directly**
```python
todo.title = title
todo.completed = completed
```
This is the interesting part: you're not writing an `UPDATE ... SET ...` SQL statement at all. You're just **changing attributes on the Python object**, like any normal object. SQLAlchemy's session is tracking this object (it came from `db.query(...)`), so it notices the change automatically.

**4. Step 3 — `db.commit()` writes the change**
```python
db.commit()
```
This is what actually generates and runs the `UPDATE` SQL behind the scenes, based on what changed on the tracked object. This "just change the attribute, then commit" style is one of the biggest conveniences of using an ORM over raw SQL.

**5. `db.refresh(todo)` — same role as in CREATE**
Re-syncs the Python object with what's now actually stored in the database, ensuring the returned data reflects the true saved state (in case the database changed anything on write, e.g. defaults or triggers).

**6. `title` and `completed` are query parameters here — same caveat as lecture 15**
```python
def update_todo(todo_id: int, title: str, completed: str, db: Session = Depends(get_db)):
```
`todo_id` is a path parameter, but `title` and `completed` are plain `str` types not typed as a Pydantic model — so per the rule from lecture 7, they're **query parameters**, not a JSON body. Call pattern:
```
PUT /todos/1?title=Buy%20milk&completed=True
```
As mentioned in lecture 15's notes, a more typical real-world design would use a Pydantic model (like `Todo` from lecture 4) for the body instead — worth keeping in mind as these lectures likely converge on that pattern eventually.

**7. Full CRUD comparison so far**
| Operation | Pattern |
|---|---|
| Create | build object → `db.add()` → `db.commit()` → `db.refresh()` |
| Read | `db.query(Model).filter(...).first()` / `.all()` |
| Update | fetch object → mutate attributes → `db.commit()` → `db.refresh()` |
| Delete | *(likely next lecture)* |

Notice Create and Update share the exact same "commit + refresh" ending — the only real difference is whether you're building a brand-new object or mutating an existing one.

## Quick recap
- Fetch the row first with `.filter(...).first()`, then guard against `None` with `HTTPException`
- Update by directly assigning new values to the object's attributes — no manual SQL needed
- `db.commit()` detects the changes and writes the `UPDATE` to the database
- `db.refresh()` re-syncs the object with the saved database state
- Still using query params here for input — a Pydantic body model is the more typical approach for real projects
