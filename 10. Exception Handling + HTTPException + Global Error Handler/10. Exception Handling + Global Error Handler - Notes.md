# 10. Exception Handling + HTTPException + Global Error Handler

## What this code does
Goes one level beyond `HTTPException` (lecture 9) by creating a **custom exception class** and a **global handler** for it — useful when you want consistent, reusable error behavior across your app.

```python
from fastapi import FastAPI, HTTPException, Request
from fastapi.responses import JSONResponse

app = FastAPI()

class UserNotFoundException(Exception):
    def __init__(self, name: str):
        self.name = name

@app.exception_handler(UserNotFoundException)
def user_not_found_handler(request: Request, exc: UserNotFoundException):
    return JSONResponse(
        status_code=404,
        content={
            "status": "error",
            "message": "User not found"
        }
    )

@app.get("/users/{user_name}")
def get_user(user_name: str):
    if user_name != "vaidik":
        raise UserNotFoundException(user_name)
    return {"name": user_name}
```

## Key concepts

**1. Custom exception class**
```python
class UserNotFoundException(Exception):
    def __init__(self, name: str):
        self.name = name
```
This is a plain Python exception (inherits from `Exception`), not FastAPI-specific. It's just a way to give your errors a **meaningful name** and carry extra data — here, `name`, so the handler knows *which* user wasn't found.

**2. Registering a handler — `@app.exception_handler(...)`**
```python
@app.exception_handler(UserNotFoundException)
def user_not_found_handler(request: Request, exc: UserNotFoundException):
```
This tells FastAPI: "whenever `UserNotFoundException` is raised **anywhere** in the app, run this function instead of letting it crash the request." It always receives:
- `request` → the incoming request object
- `exc` → the actual exception instance that was raised (so you can access `exc.name`, etc.)

**3. Returning a custom response — `JSONResponse`**
```python
return JSONResponse(
    status_code=404,
    content={"status": "error", "message": "User not found"}
)
```
Unlike `HTTPException` (which has a fixed `{"detail": "..."}` shape), `JSONResponse` lets you fully control the response body's structure — here using `status` and `message` keys instead. This is useful if your API has a consistent custom error format across all endpoints.

**4. Raising it like a normal exception**
```python
raise UserNotFoundException(user_name)
```
From the route's perspective, this looks just like raising any Python exception — no need to know about status codes or response formatting *inside* the route itself. That logic lives centrally in the handler.

**5. Why this is better than repeating `HTTPException` everywhere**
Compare to the commented-out old version at the bottom (raising `HTTPException` directly inside the route). The custom exception approach means:
- **Centralized formatting** — if you want to change what a "not found" error looks like, you edit it in **one place** (the handler), not every route
- **Cleaner routes** — routes just raise a meaningful, named exception; they don't need to know response formatting details
- **Reusable** — any route in the app can raise `UserNotFoundException` and get the same consistent behavior

**6. `HTTPException` vs custom exceptions — when to use which**
- `HTTPException` → quick, one-off errors, built-in and simple (good for smaller apps or unique cases)
- Custom exception + handler → better when the **same kind of error** happens in multiple places and you want consistent formatting/behavior everywhere

## Quick recap
- `class MyError(Exception):` → define a custom, meaningful exception, optionally carrying extra data
- `@app.exception_handler(MyError)` → registers a **global handler** that runs whenever `MyError` is raised anywhere in the app
- Handler returns a `JSONResponse` with full control over status code and body shape
- Routes simply `raise MyError(...)` — clean, and the error-formatting logic stays centralized in one handler
- Use this pattern when a specific error type repeats across your app and you want consistent handling
