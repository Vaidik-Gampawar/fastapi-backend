# 21. JWT Authentication + Token-Based Auth + Login API

## What this code does
Upgrades the simple hardcoded-token auth from lecture 11 to **real JWT (JSON Web Token) authentication** — a login endpoint that issues a signed token, and a protected route that requires a valid token to access.

```python
# pip install python-jose

from fastapi import FastAPI, Depends, HTTPException, Header
from jose import jwt
from datetime import datetime, timedelta, timezone

app = FastAPI()
SECERT_KEY = "mysecert"
ALGORITHM = "HS256"

def create_token(data: dict):
    to_encode = data.copy()
    expire = datetime.now(timezone.utc) + timedelta(minutes=30)
    to_encode.update({"exp": expire})
    token = jwt.encode(to_encode, SECERT_KEY, ALGORITHM)
    return token

@app.post("/login")
def login(username: str, password: str):
    if username != "admin" and password != "1234":
        raise HTTPException(status_code=401, detail="Invalid Username or Password")
    token = create_token({"sub": "admin"})
    return token

def verify_token(token = Header(None)):
    try:
        payload = jwt.decode(token, SECERT_KEY, algorithms=[ALGORITHM])
        return payload
    except:
        raise HTTPException(status_code=401, detail="Invalid or Expired Token")

@app.get("/secure")
def secure_route(user = Depends(verify_token)):
    return {"message": "Secure Data Accessed", "user": user}
```

## ⚠️ Bug worth fixing: `and` should be `or`
```python
if username != "admin" and password != "1234":
```
As written, this only rejects the login if **both** the username is wrong **and** the password is wrong. That means:
- `admin` / `wrongpassword` → logged in (password is ignored, since username matched!)
- `wronguser` / `1234` → logged in (username is ignored, since password matched!)

This should be:
```python
if username != "admin" or password != "1234":
```
So the login is rejected if **either** field is wrong. This is exactly the correct version from lecture 11, so it's likely a typo here — worth double-checking your own version of this file before building on it further.

## Key concepts

**1. What a JWT actually is**
A JWT is a signed piece of text representing some data (like "this user is admin"), split into three parts: header, payload, and signature. It's not encrypted (anyone can read the contents), but it **is signed**, so tampering with it can be detected. This is different from lecture 11's approach, where you compared a hardcoded string — a JWT instead *proves* who issued it and that it hasn't been altered.

**2. `create_token(data: dict)` — building the token**
```python
def create_token(data: dict):
    to_encode = data.copy()
    expire = datetime.now(timezone.utc) + timedelta(minutes=30)
    to_encode.update({"exp": expire})
    token = jwt.encode(to_encode, SECERT_KEY, ALGORITHM)
    return token
```
- `data.copy()` → avoids mutating the original dict passed in
- `expire = ... + timedelta(minutes=30)` → calculates a timestamp 30 minutes from now
- `to_encode.update({"exp": expire})` → adds an `exp` (expiration) claim — a standard JWT field that makes the token automatically invalid after this time
- `jwt.encode(to_encode, SECERT_KEY, ALGORITHM)` → signs the data using your secret key and algorithm (`HS256`), producing the final token string

**3. `SECRET_KEY` and `ALGORITHM`**
The secret key is what allows your server to **sign** tokens and later **verify** they weren't tampered with. Anyone with this key could forge valid tokens, so in a real app it must be kept secret (e.g. in an environment variable, never hardcoded like `"mysecert"` here). `HS256` is the signing algorithm being used.

**4. The login route — issuing a token**
```python
@app.post("/login")
def login(username: str, password: str):
    ...
    token = create_token({"sub": "admin"})
    return token
```
- `"sub"` is a standard JWT claim name meaning "subject" — typically the identity the token represents (here, hardcoded to `"admin"`; in a real app this would usually be the actual authenticated username or user ID)
- The route checks credentials, and if valid, returns a signed token the client should store and send with future requests

**5. `verify_token()` — decoding and validating**
```python
def verify_token(token = Header(None)):
    try:
        payload = jwt.decode(token, SECERT_KEY, algorithms=[ALGORITHM])
        return payload
    except:
        raise HTTPException(status_code=401, detail="Invalid or Expired Token")
```
- `jwt.decode(...)` → verifies the token's signature (proving it was issued by this server and not tampered with) **and** checks the `exp` claim automatically — an expired token will fail to decode
- If decoding fails for any reason (invalid signature, expired, malformed) → the `except` block catches it and raises a `401`
- This directly reuses the `Depends()` + `Header()` pattern from lecture 11, just with real cryptographic verification instead of a hardcoded string comparison

**6. The protected route**
```python
@app.get("/secure")
def secure_route(user = Depends(verify_token)):
```
Same dependency injection pattern as lecture 11 — `verify_token` runs first, and only if it succeeds does `secure_route` execute, receiving the decoded token payload (e.g. `{"sub": "admin", "exp": ...}`) as `user`.

**7. The typical JWT flow, end to end**
```
1. Client → POST /login with username/password
2. Server verifies credentials, issues a signed JWT (with expiry)
3. Client stores the token, sends it in the "token" header on future requests
4. Server verifies the signature + expiry on each protected request
5. If valid → request proceeds; if not → 401
```

## Comparing to lecture 11's simple auth
| | Lecture 11 (hardcoded token) | Lecture 21 (JWT) |
|---|---|---|
| Token check | `token != "mysecerttoken"` | Cryptographic signature verification |
| Expiration | None — token works forever | `exp` claim, auto-expires (30 min here) |
| Identity info | None carried in the token | `sub` and other claims carried in the payload |
| Realistic for production | No — a fixed shared secret | Closer, though secret key management, refresh tokens, and secure token storage would still need work |

## Quick recap
- JWTs are signed (not encrypted) tokens that carry claims like `sub` (subject) and `exp` (expiration)
- `jwt.encode(payload, secret, algorithm)` → creates a signed token
- `jwt.decode(token, secret, algorithms=[...])` → verifies signature and expiry, raises an error if invalid
- Login route issues the token after checking credentials; protected routes use `Depends()` to verify it before running
